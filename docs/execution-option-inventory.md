# Execution-option inventory

## Scope and implementation status

This is the workstream 1 contract inventory for [daemon-first design](daemon-first-design.md), checked against the cooperative worktree on September 6, 2026. It describes implemented request validation and daemon-backed clients, not a claim that the whole migration has shipped. Ordinary `run` and ACP execution use the daemon unconditionally; SDK-launched ACP is a thin client, not another provider/runner owner.

The source inventory is `cmd/kodelet/main.go`, `run.go`, `run_remote.go`, and `tracing.go`; `pkg/chat/chat.go`, `execution_options.go`, and `turn.go`; `pkg/types/llm/config.go`, `config_snapshot.go`, and `execution_options.go`; and the TypeScript session/extension API in `sdk/src/{agent,execution,child}.ts`. Python parity was implemented and tested in the separately maintained sibling checkout `../kodelet-python-sdk`, including actual extension and ACP process-boundary fixtures. Coordinated SDK publication is still a release task, not implied by local verification.

**Dispositions:** **Supported** means the current daemon-backed CLI/API implements the described mapping, or the setting remains explicitly client-owned. **Replaced** means the invocation-level setting must instead be configured at its stated owner; the remote CLI rejects the old explicit flag. **Removed** means there is no corresponding remote execution mode. **Gap** qualifies an intended disposition whose client adapter or compatibility behavior is not implemented; it must not be read as support.

**Persistence notation:** **Snapshot** means effective model/request semantics are recorded in `config_snapshot` and locked for a conversation. **Run only** means the option is not persisted as a default for the next submission; messages and results still persist. **Affinity** means the daemon retains the conversation's runner, environment profile, and CWD binding. **Client only** means no execution configuration is persisted for that setting. None of these creates a no-save conversation mode.

## Typed execution contract

`ChatRequest.options` is an optional, credential-free `ExecutionOptions` object with camelCase JSON names. Request overrides, SDK session options, and registered extension presets use this subset, not `Config`, arbitrary YAML, credentials, endpoints, executable paths, or runtime objects. Of these options, the runner receives only `Restrictions()`: model, reasoning, token, turn, and weak-model-selection fields remain central. A model profile identifier may separately select locally pinned environment settings for the embedded runner; this is not broad configuration or credential transport.

Omission inherits the owning configuration. `{}` is an explicit object with no overrides. `false`, `0`, and `[]` are retained rather than treated as omission. `options: null`, null-valued option fields, unknown option fields, non-object options, wrong types, empty/NUL-containing strings, and invalid numeric values are rejected. Failed decoding does not partially replace a retained request/options object. A Go caller can use nil to represent an absent options pointer; a non-nil pointer to a zero-length allowlist represents deny-all.

For example, `{"options":{"noTools":false,"allowedTools":[],"maxTurns":0}}` is tool-free with no turn-count limit: the empty allowlist still denies all model-callable tools. `allowedCommands: []` disables bash, not unrelated tools. Legacy `Config.allowed_tools: []` and `allowed_commands: []` instead mean unrestricted; they must not be substituted for request deny-all markers.

Model selection is a catalog/configuration rule, **not a configurable per-user model allowlist**: Anthropic uses its built-in pricing catalog plus the effective main/weak models and aliases. OpenAI additionally accepts configured reasoning/nonreasoning model lists and pricing keys; ordinary OpenAI and Codex use their respective built-in catalogs. Other OpenAI-compatible platforms do not gain the ordinary OpenAI catalog implicitly, but configured models and aliases remain accepted. Alias targets include built-in aliases added during configuration loading. The validator does not query a provider to prove that a model is available to an account, enforce account-level spending limits, or impose a separate maximum-turn/token ceiling. Such provider availability and budget policy are not implemented by this schema.

`main.go` contains a vestigial Viper lookup for `--weak-reasoning-effort`, but no such CLI flag is registered and there is no corresponding execution-option field. It is not a supported additional override; supplying the flag fails CLI parsing.

Model/provider/token/reasoning values are frozen in the persisted conversation snapshot. Repeating the same effective values is allowed; changing them is rejected against the stored snapshot, not merely against the incoming live config. Legacy conversations without `config_snapshot` cannot supply model overrides, even unchanged ones. Current live credentials/endpoints and environment policy are not taken from the snapshot. The existing snapshot contract permits a frozen conversation's reasoning effort to outlive later creation-time policy changes.

### Restrictions and runner policy

| CLI option | Disposition and wire | Owner | Omitted/default | Persistence | Policy and error behavior |
|---|---|---|---|---|---|
| `--no-tools` | Supported: `options.noTools` | Daemon and runner | No additional disablement | Run only | True denies all model-callable built-in, extension, and provider-native tools. False cannot override an empty allowlist or an inherited true restriction. Internal lifecycle/administrative operations are not model-callable tools. |
| `--allowed-tools` | Supported: `options.allowedTools` | Daemon and runner | Inherit host tool policy | Run only | `[]` denies all. Nonempty lists are intersected with host restrictions, never widened. Unknown nonempty names simply match no available capability; there is no separate unknown-tool-name validation. |
| `--allowed-commands` | Supported: `options.allowedCommands` | Runner; daemon can narrow before forwarding | Inherit host command policy | Run only | `[]` disables bash. Nonempty lists reach bash's command validator. Host/request pattern intersection is by exact pattern-string equality, not semantic glob subset analysis; disjoint lists deny bash. Empty/NUL-containing entries fail validation. |
| `--no-extensions` | Supported: `options.noExtensions` | Runner | Inherit configured extension availability | Run only | True disables extension discovery/runtime construction for this execution. False cannot enable extensions disabled by host or inherited policy. It is not equivalent to disabling all tools. |
| `--no-skills` | Supported: `options.noSkills` | Runner | Inherit skill availability | Run only | True disables skills; false cannot enable host-disabled skills. It does not change the host's allowed-skill list. |
| `--enable-fs-search-tools` | Supported: `options.enableFSSearchTools` | Runner | Runner's configured filesystem-search availability | Run only | False disables `glob_tool`/`grep_tool`; true cannot enable a feature disabled by runner/inherited policy and fails explicitly in that case. |

`Config.Clone()` copies mutable provider settings, aliases, tool/command/effort lists, prompt arguments, skills/context, system information, execution-option pointers/lists, and nested profile/extension settings maps and slices, including typed Go containers. It deliberately retains the identity of opaque active extension runtimes. A clone is an independent settings snapshot, not a synchronization primitive for concurrent mutation of its source during cloning. Run-only restrictions are excluded from JSON/YAML `Config` serialization and from persisted model snapshots.

`ApplyEnvironmentOptions` applies only environment restrictions before tool/extension discovery and rejects model/turn fields on the runner boundary, including explicit `maxTurns: 0` and `useWeakModel: false`. Already inherited deny-all lists and true disablements cannot be removed by applying omitted, false, or wider later overrides. Empty command denies retain their explicit marker even though legacy `Config` empty lists mean unrestricted. Another independent submission starts from its own owning configuration, not the previous request's restrictions.

There is currently no schema for **mandatory-enabled** extensions or skills. `extensions.enabled: true` and `skills.enabled: true` are availability defaults, not a requirement that a run must keep them enabled. The design's future policy-conflict error for disabling a mandatory feature therefore cannot be advertised as implemented. Mandatory **disables** and allowlist upper bounds are enforced by the restrictions above.

`KODELET_CONFIG_FILE` supplies trusted defaults to its owning process, merging after the user file unless `KODELET_CONFIG_FILE_MODE=isolated` omits that file. Neither mode uploads client configuration or bypasses the runner's per-CWD workspace policy. Global process loading never imports `kodelet-config.yaml`: both standalone and embedded runners independently load its permitted environment fields at the canonical execution CWD, beneath trusted environment profiles and request restrictions. Repository provider/model/endpoint settings and profile definitions are not imported into daemon configuration. Remote model/restriction overrides come only from explicit mapped flags; shell variables such as `KODELET_MODEL` do not implicitly rewrite a running daemon. A newly activated shell virtual environment or arbitrary SDK `env` values are not per-run environment injection into an already-running runner.

### Embedded runner configuration inheritance

The embedded runner inherits the trusted daemon's top-level environment subset: `tool_mode`, `sysprompt`, `sysprompt_args`, `enable_fs_search_tools`, `bash`, `context`, `skills`, `extensions`, `allowed_tools`, `allowed_commands`, `allowed_domains_file`, and `environment_profiles`. The selected daemon model profile contributes its environment subset per run, rather than requiring operators to duplicate it in `serve.runner_settings`.

Preference precedence, from lowest to highest, is: daemon base/defaults → selected model profile environment settings → explicit `serve.runner_settings` → permitted per-CWD repository settings → selected trusted environment profile → request narrowing. Explicit runner settings override preferences such as `tool_mode`, `sysprompt`/`sysprompt_args`, `enable_fs_search_tools`, `context`, and `bash`, and may narrow permissions. Repository settings cannot widen effective trusted runner constraints, including `skills.allowed`, extension allow/deny and per-tool settings, and `allowed_domains_file`, or define either kind of profile. Request options only narrow the resulting policy.

The selected daemon model/base configuration's `allowed_tools`, `allowed_commands`, `skills.enabled: false`, and `extensions.enabled: false` are mandatory ceilings already sent on normal remote runs. These four inherited restrictions intersect with runner policy (deny wins), not last-write-wins; neither `serve.runner_settings` nor trusted environment profiles can relax them. The embedded loader applies `inherited.EnvironmentOptions` before discovery, so discovery and actual runs enforce the same ceilings even when explicit runner settings attempt widening.

The `ProfileConfigLoader` hook resolves the model profile identifier against locally pinned trusted environment projections. `default` selects the daemon base, blank selects the daemon's active default, and a named identifier selects that profile. A saved conversation whose named model profile has been removed preserves the daemon's existing fallback to the base environment, not the active named default, while retaining its snapshotted model identity; unknown names still fail for new conversations. No model/provider configuration, endpoints, or credentials are passed in runner settings, and no broad `Config` transport is introduced. Standalone runners retain their own environment preferences while enforcing the daemon restrictions sent with remote runs.

Trusted defaults and profile definitions are pinned at startup; restart `kodelet serve` to apply changes, including explicit runner settings. Both embedded and standalone runners resolve trusted `environment_profiles` before resource discovery. Each embedded run uses an independent settings snapshot when applying its model profile, CWD repository settings, environment profile, and request restrictions; nested settings and restrictions must not leak into pinned defaults, later runs, or concurrent runs. Per-CWD repository changes affect later runs, not active ones.

## Completion, cancellation, and uncertain submissions

The current remote one-shot adapter generates conversation and turn IDs, uses the existing streamed chat API, consumes explicit `result`/`done` information, and returns an error for failed execution or a missing required final result. CLI errors produce nonzero exit status; acknowledged cancellation is represented as `context.Canceled` and the CLI exits 130. Successful streaming and final-only runs both use daemon persistence.

Transport loss detaches the client; it is not proof that daemon-owned execution stopped. Explicit interruption attempts an exact-conversation/turn stop with a fresh bounded context. If acknowledgement fails, the client reports that work may still be running. The daemon commits a durable `(conversationId, turnId)` receipt with an input fingerprint and reserved `runId` before execution. The same IDs and normalized input return pending status (`202`) or the recorded terminal result/error; different input conflicts (`409`). No tool or transient event replay is performed. UI capabilities are observer state and do not change the fingerprint; explicit execution restrictions do.

`GET /api/conversations/{id}/turns/{turnId}`, Go `GetTurnReceipt`, and `kodelet conversation turn <conversation-id> <turn-id>` query status/result without submission. Status is `accepted`, `running`, `succeeded`, `failed`, `cancelled`, or `interrupted`. A missing receipt is not proof that an in-flight request can no longer arrive: exact stop creates a durable early-cancellation fence. Pending cancellations survive restart; unfinished non-cancelled turns become interrupted rather than restarting. Query success means status retrieval, not successful execution. Receipts/tombstones are retained independently of history deletion to preserve deduplication; no retention/compaction policy or transparent restart continuation is implemented.

## Verification and explicit limitations

Focused tests in `pkg/types/llm/execution_options_test.go`, `config_test.go`, and `pkg/chat/execution_options_test.go` cover omitted/false/zero/empty values; strict request/options decoding; denied tool classes; host/inherited restrictions; typed settings cloning; independent requests; provider/catalog/configured-model selection; frozen model metadata; legacy override rejection; and rejection before runner resolution, extension runtime initialization, or provider-thread creation. These tests use local configuration/store fixtures and no provider calls.

Remaining limitations are explicit: mandatory-enabled feature policy; arbitrary user-session prompt/resource-root upload; per-run shell-environment transport; provider-account availability or spend ceilings; SDK release publication and separately maintained extension migration; and durable receipt retention policy. Legacy affinity adoption is a separate validated workflow, not implicit rebinding by execution options. Completed workstream, physical-placement, public-client, and cutover verification is recorded in the [design document](daemon-first-design.md#completed-verification-record-september-6-2026); local acceptance does not imply SDK publication or live external-service verification.
